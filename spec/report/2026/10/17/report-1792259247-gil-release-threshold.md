## Report on task: GIL-release threshold (fixes multi-thread cold-scan degradation)

Ad-hoc owner request: fix the rurex degradation on GIL Python visible
in the Telegram benchmark (cold @mention scan: 1.65 s single-threaded
escalating to 5.38 s across four workers). Also: benchmark results
must be Markdown, not HTML.

### Done

- **Root cause** (probes in `var/convoy_probe*.py`, switch-interval
  sweep + `re` control): every `findall` released and immediately
  re-acquired the GIL around a ~0.2 µs scan — a million handoffs per
  pile, each a scheduler wake of a GIL-waiting thread. Not the
  classic `gil_drop_request` convoy (switch interval 5 ms/50 ms/1 s
  changed nothing); `re` (never releases during matching) was immune
  at every config; free-threaded scaled cleanly.
- **Fix** (`src/regex.rs`): `GIL_RELEASE_MIN_HAY = 4 KB` + the
  `maybe_detach(py, hay_len, f)` helper — release the GIL only when
  the haystack is ≥ 4 KB (≈0.4 µs of scan at ~11 GB/s; a 100×-slower
  pattern stays under 1 ms GIL-held, and `re` never releases at any
  size). Applied at the 18 per-op detach sites (findall, search,
  match/prefixmatch, fullmatch, is_match, FindIter::step, split,
  substitute, scanner; str and bytes).
- **Validated**: convoy probe cold 4-thread 1.78 s → 0.51 s
  (perfectly flat vs single-thread); full Telegram re-run — GIL
  rurex now flat at 1.55–1.88 s across 1–4 workers (was 1.65→5.38);
  free-threaded scaling preserved (1.76→0.53 s). Main benchmark
  suite re-run: Tests 6–7 unchanged (1 MB haystacks sit far above
  the threshold, GIL-released scans still scale; rurex 0.80→0.51→
  0.77→0.82 s), Tests 1–5 within noise. All test walls green
  (fmt/clippy/cargo/pytest 279 + three conformance suites).
- **Docs → Markdown**: `docs/telegram-benchmarks.md` is now the
  committed document (charts as committed PNGs in `docs/img/`,
  numbers rendered from `telegram_results.json`); the HTML twin is
  generated by `telegram_charts.py --html` and gitignored, matching
  the main page's convention. `docs/benchmarks.md` tables and inline
  figures refreshed to the new run.
- **Incident + recovery**: the earlier history reset that dropped the
  unpushed Telegram commits also cut the never-pushed divergences
  commit (it sat between `origin/main` and the dropped tip), and the
  follow-up gc pruned its objects. The suite was fully reconstructed
  from session records + the /tmp vendor copy (sha256 unchanged),
  re-committed, and re-verified (1,078 tests green, identical ledger:
  208 rows / 0 discuss).

### Postscript: bytes variant added to the Telegram benchmark

Owner follow-up: every point now runs two input forms (str and
pre-encoded UTF-8 bytes, preparation untimed, one compile per matrix
item). 32 cold runs. The bytes variant is the headline resolution of
the ×3 discussion: rurex bytes **0.35 s beats re bytes 0.51 s
(×1.5)** single-threaded on GIL Python — the feed-UTF-8-bytes shape
RE2's own binding recommends — while the str variant keeps the
honest ×3 story (CPython's per-string transcode; near-parity warm).
Free-threaded: both variants scale (rurex bytes 0.43 → 0.30 s at
4 workers). Committed as 07b3423.

### Postscript 2: three-way UTF-8 borrow (the str-path follow-up)

Implemented the owner-approved hybrid (`src/utf8.rs`): compact-ASCII
strings borrow the internal buffer zero-copy; non-ASCII strings with
CPython's utf8 cache warm borrow it; cold non-ASCII strings transcode
in Rust into an owned buffer. CPython's cache is never written.
Correctness: 31 Rust tests (incl. encoder byte-equality over a
torture corpus + ABI-offset validation), pytest 279, CPython vendored
suite, all three corpus suites green.

**Honest result: the cold-str gap did not close.** GIL single-thread
1.49 → 1.46 µs/post. The Rust scalar transcoder
(`String::from_utf16`) runs at 0.48 GB/s on Arabic UCS-2 — the same
class as CPython's own encoder (~0.45 GB/s). Micro-benchmarks
(`var/utf8_micro.md`): from_utf16 0.48 GB/s, encoding_rs 0.81 GB/s
(1.7×), manual push 0.48 GB/s. To reach the ×1.4-1.5 target the
transcoder must hit 5-10 GB/s — SIMD territory (encoding_rs
`simd-accel`, xutf, or simdutf; the latter is a C++ dependency).

What the change does deliver: ASCII haystacks and cache-warm strings
now skip the CPython encoder entirely (measurable on any workload
whose strings were pre-touched by another C-API consumer), the
groundwork for a SIMD transcoder behind the same `utf8_of` signature,
and correct semantics for all three storage kinds.
