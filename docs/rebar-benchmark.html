rebar: rurex against stdlib re and the Rust engine

rebar is BurntSushi's barometer for comparing regex engines on a curated set of tasks. This page reports how rurex fares on it against the two engines a Python user actually weighs it with: the standard library's re, which it replaces, and rust/regex, which it embeds.

The metric is rebar's own: each benchmark divides an engine's median time by the fastest median among the engines that ran it, and an engine's score is the geometric mean of those ratios across the benchmarks all three share. Lower is faster; 1.0 is the fastest engine on that set. A score of ×3 means "typically three times the best engine's time".

rurex sits between the engine it embeds and the module it replaces: about 3.7× faster than re on average, and about 2.7× off the Rust engine. The distance to the engine is not the scanner: the two run the same automata. It is the Python boundary — argument handling and one Python object per match — plus, on non-ASCII text, the cost of materialising UTF-8.

re wins 10 of the 44 shared benchmarks, and they fall into three groups:

  • Compile time (3 points): re's parser is cheaper than building the automata for these patterns. rurex parses an accepted pattern once (ADR-0015), so what remains is the engine's own compile: 03-date/compile-unicode costs 5.66 ms against re's 3.69 ms, while rust/regex itself takes 5.72 ms; 10-bounded-repeat/compile-capitals costs 72.17 µs against re's 27.59 µs, engine 61.23 µs.
  • Match-heavy iteration (1 point): rebar's counting models call m.group(0) per match, so a haystack with tens of thousands of matches measures the Python object per match plus the accessor call. In 08-words/all-english (an ASCII haystack in text mode, so no transcode, with 56,601 matches) rurex takes 2.76 ms against 2.25 ms for re and 695.72 µs for the engine alone: about 49 ns per match for rurex, 40 for re, and 12 for the engine's own loop. The object is a Match per match (ADR-0016); the rest is the per-call boundary.
  • Unicode word boundaries on non-ASCII text (2 points, all-russian and long-russian): the engine itself is slower than re here — rust/regex takes 5.99 ms against re's 2.95 ms — because its fast DFA cannot handle a Unicode-aware \b on non-ASCII bytes and falls back to a slower engine. rurex adds its per-match objects on top (9.20 ms total); its transcode of this 130 KB haystack is about 65 µs, under 1% of the call. Beating re there is not a binding task.
  • Near parity scans (4 points): within 15% of each other, with re marginally ahead.

rurex wins the other 34 points, sometimes by four orders of magnitude: re is a backtracker, and rebar's dictionary and ReDoS benchmarks make that visible.

Text mode versus byte mode, identical input

dictionary/search/english-15 runs in Unicode mode over an ASCII haystack, so the two representations are interchangeable for the match count. rurex's text path borrows ASCII strings instead of transcoding them, which is why the two modes are within a couple of percent here; what remains against the Rust engine is the Python boundary.

engine throughput
rust/regex 687 MB/s
python/rurex-bytes 677 MB/s
python/rurex 663 MB/s
python/re 166 KB/s

The non-ASCII case is the interesting one, and rebar cannot measure it without changing match counts: on a Russian or Chinese haystack the byte engine matches ASCII word characters only. That comparison lives in telegram-benchmark.md, where the text row pays one UCS→UTF-8 encode per post and the byte row pays none.

What this does and does not say

  • rebar's counting models iterate finditer, so one Python object per match is inside the measurement. That is what a finditer user pays, but it is not what findall pays: rurex's findall path builds strings directly, with no Match objects, and rebar has no model for it. The per-match numbers here therefore overstate the cost for findall-shaped workloads.
  • Most rebar benchmarks set unicode = false, i.e. they hand every engine bytes. Those points measure the path with no transcoding at all; the transcode appears only in the Unicode-mode benchmarks (03-date/unicode, the Russian and Chinese literals and words).
  • The ranking is a geometric mean across heterogeneous tasks. Read the per-group and per-benchmark tables for anything decision-shaped; the mean is a summary, not a measurement of your workload.

Reproducing

benchmarks/rebar/README.md holds the runner, the engine registration and the full invocation. The short version, on the benchmark host:

python3 benchmarks/rebar_run.py          # measure, verify, then rebuild this page

which takes the core lease, pins to CPU 0, runs rebar for the four engines, and calls benchmarks/rebar_charts.py only if every point passed.
