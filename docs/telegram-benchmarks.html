rurex — Telegram @mention extraction benchmark

Real-world task, measured exactly as performed: one pass of findall over every post's text — one search, once, on a corpus that has never been scanned before. Each measured point is a fresh interpreter process that loads the corpus and performs the single pass split across N barrier-started workers. There is no warm-up and no repeat scan; nothing is measured twice.

  • Pattern (Telegram username rules — 5–32 chars, [a-zA-Z0-9_], starts with a letter): @[a-zA-Z][a-zA-Z0-9_]{4,31}
  • Corpus: 1,000,000 posts, 470 MB of text (mostly Arabic/Persian), 334,136 mentions in 186,226 posts (18.6% of posts, ≈0.33 mentions per post). Provenance and SHA-256: benchmarks/telegram/PROVENANCE.md.
  • Timing window: from the instant a worker passes the barrier to the instant its slice is finished; the point is the max across workers. JSONL load and pattern compile are outside the window, identically for both engines. Verified by a mention-count checksum (334,136 per run).
  • Interpreters: GIL CPython 3.13 and free-threaded 3.14t, each as fresh subprocesses. CPU: Intel(R) Core(TM) i5-8350U CPU @ 1.70GHz.

Single-threaded, re answers the whole pile in 0.48 s and rurex in 1.65 s. Most of rurex's gap is CPython's first-touch UTF-8 materialization: CPython stores str in a UCS-1/2/4 form and lazily encodes-and-caches a UTF-8 copy inside each string the first time anything asks for it — which is exactly what rurex (like any UTF-8 engine consuming Python strings) must do, via PyUnicode_AsUTF8AndSize. re never converts — its engine walks the native form — so it pays nothing. Over 470 MB of mostly non-ASCII text that is a one-time ~1 s encode, inside the measured run because a scan-once user pays it.

Adding threads makes rurex's cold scan worse on the GIL build (1.65 s → 5.38 s at four workers): the per-string UTF-8 allocation happens in rurex's GIL-held section, and the pile performs a million detach/attach cycles around the scans — a GIL convoy whose overhead grows with the thread count. re is roughly flat (0.48–0.66 s).

Without the GIL the same cold scan scales cleanly: rurex 1.46 s → 0.52 s at four workers (2.8×) — the first-touch UTF-8 encoding parallelizes like any other work — and re 0.42 s → 0.33 s. On this scan-once task free-threaded Python is the fastest way to run rurex at every thread count.

Reading the numbers

This is the extraction-bound regime — short texts, ≈0.33 matches per post, per-call overhead dominating — the opposite of the scan-bound workloads on the main benchmark page, where rurex leads by 7–13× single-threaded. Here re wins every point: partly per-call fixed cost, and partly the one-time UTF-8 tax that only the UTF-8 engine pays. Users who scan each text exactly once pay it once; users re-scanning re-use the cached UTF-8 form and the tax vanishes. Machine-specific; expect different absolute numbers elsewhere.
