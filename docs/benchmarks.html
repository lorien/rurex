Benchmarks: rurex vs re

Three parameter-sweep benchmarks comparing the linear-time engine to the standard library's backtracking engine, measured end to end from Python — including every bit of object construction a real user pays for. Every chart has two axes: the variable parameter (input size, match position, density, ...) on X and time per operation on Y.

  • Test 1 — Scan: rurex up to 8.6× faster, and the gap widens with input size.
  • Test 2 — Extraction: an honest crossover — rurex wins when matches are sparse (4.7× at 5 matches/KB), re wins when they are dense (2.2× at 160 matches/KB).
  • Test 3 — Pathological: re never finishes; rurex answers in ~250 ns at any size.

A rendered, standalone HTML twin of this page (images embedded) lives at benchmarks.html — open it directly in a browser.

Methodology

  • Parameter sweeps. Each test varies one parameter across a range (log-spaced where sensible) and measures the operation at every point for both engines; charts plot parameter vs time.
  • End-to-end timing. The Python-visible operation is timed (method call → returned objects), not the engine in isolation. rurex's per-match Python-object construction is included — that is the honest number a user experiences.
  • Timing protocol. timeit-style auto-calibrated iteration counts (≥ 0.2 s of work per measurement), median of 3 repeats. The pathological test is single-shot under a 2 s timeout guard on re, because its runtime explodes.
  • Release build. All rurex numbers use maturin develop --release (opt-level 3, fat LTO).
  • Deterministic inputs. Haystacks are generated from fixed seeds; literal targets sit at stated positions (position 100% is the worst case: the whole text must be scanned).

Environment
CPU Intel Core i5-8350U @ 1.70 GHz

rurex 0.1.0, release profile (opt-level=3, LTO=fat)

Numbers are machine-specific; expect different absolute values and somewhat different ratios elsewhere.

Test 1 — Scan: one literal in a large haystack

A plain literal search for a single needle occurring exactly once — the classic log-grep workload and the automata engine's home turf: rurex scans with SIMD-accelerated prefilters, while re steps its backtracking VM character by character. Two parameters are swept: haystack length (needle at the end — the worst case), and needle position in a fixed 8 MB haystack.

Pattern

"the-needle-string"

Data example (word filler, one needle, truncated)

jumps delta data node item brown lorem fox alpha item world alpha text
amet node lazy fox alpha the the-needle-string …

Variable parameter: haystack size (needle at the end)

Size re rurex Speedup
64 KB 77 µs 8.9 µs ×8.6
256 KB 311 µs 36 µs ×8.6
1 MB 1.26 ms 143 µs ×8.8
4 MB 5.0 ms 695 µs ×7.2
16 MB 20.4 ms 4.9 ms ×4.2

Both engines scale linearly; rurex' constant is several times smaller. The advantage narrows slightly at 16 MB as the prefilter's advantage over memory bandwidth shrinks — scanning is memory-bound at that size.

Variable parameter: needle position (8 MB haystack)

Needle at re rurex Speedup
0% 163 ns 715 µs re ×4400
25% 2.5 ms 895 µs rurex ×2.8
50% 5.0 ms 1.19 ms rurex ×4.2
75% 7.6 ms 1.60 ms rurex ×4.8
100% 11.4 ms 2.81 ms rurex ×4.1

The one place re wins is a needle in the very first bytes, where its fast path returns almost instantly while rurex pays a fixed cost for setting up the capture machinery on the haystack (~0.7 ms here — visible as the floor of rurex' line). Past the first quarter of the text, rurex' scan speed dominates: it finds the needle at 100% four times faster than re.

Test 2 — Extraction: findall over match-dense data

Digit-run extraction over word filler — the regime where matches are small and numerous, so the cost is dominated by building Python match objects rather than scanning. rurex currently constructs each result through Python-level slicing, which is exactly what this test exposes. Two parameters are swept: data length at fixed density, and match density at fixed length (isolating per-match cost from scan cost).

Pattern

r"\d{3,4}"

Data example (digits embedded in word filler, truncated)

7685 value word word beta beta lorem node alpha word value text value
alpha word value value node al …

Variable parameter: haystack size (80 matches/KB)

Size re rurex Speedup
64 KB 2.5 ms 2.1 ms rurex ×1.2
256 KB 6.7 ms 8.5 ms re ×1.3
1 MB 25.3 ms 34.9 ms re ×1.4
4 MB 97.9 ms 128.9 ms re ×1.3

At this density the two start nearly even and re pulls ahead by ~1.3×: per-match object construction dominates, and its C loop is cheaper than rurex' Python-level result assembly.

Variable parameter: match density (1 MB haystack)

Density re rurex Speedup
5 /KB 19.1 ms 4.1 ms rurex ×4.7
20 /KB 18.6 ms 10.3 ms rurex ×1.8
80 /KB 25.7 ms 33.4 ms re ×1.3
160 /KB 28.2 ms 62.4 ms re ×2.2

This is the honest crossover chart. With sparse matches, scanning dominates and rurex is up to 4.7× faster; as matches multiply, the per-match cost takes over and re wins by up to 2.2×. Your workload's density decides which engine to use.

Test 3 — Pathological: catastrophic backtracking

The pattern (x+x+)+y never matches a run of x's — and for a backtracking engine, the number of ways to distribute the x's across the nested groups grows exponentially: re's time doubles with every two extra input characters. A finite-automata engine cannot backtrack, so rurex' time is flat. This is a safety property (ReDoS resistance), not a speed feature: no pattern and no input can make rurex blow up.

Pattern

r"(x+x+)+y"

Data example

xxxxxxxxxxxxxxxxxxxxxxxx    (n = 24 of the sweep; no y — nothing matches)

Variable parameter: input length n ("x" * n)

n re rurex
8 24 µs 229 ns
12 236 µs 222 ns
16 3.9 ms 238 ns
20 59.9 ms 236 ns
24 966 ms 242 ns
26 ≥ 2 s — still running at the timeout 246 ns
28 — 248 ns

Extrapolating re's doubling curve, n=40 would take longer than the age of the universe. rurex answers every input in a quarter of a microsecond, and would keep doing so at n=40, n=400, n=4 million.

Reproducing

python -m venv .venv && source .venv/bin/activate
pip install maturin pytest matplotlib markdown
maturin develop --release          # release build — mandatory

python benchmarks/run.py           # runs the suite, writes results.json
python benchmarks/make_charts.py --html   # charts + docs/benchmarks.html

benchmarks/suite.py defines the three tests (patterns, data generators, sweep parameters); benchmarks/run.py is the harness (auto-calibration, medians, timeout guard, environment capture); benchmarks/make_charts.py regenerates the charts and the HTML render from results.json. This page's numbers come from the environment above; regenerate on your own hardware before making decisions that depend on them.

Raw results: benchmarks/results.json. Numbers on this page were measured on 2026-10-16 with rurex 0.1.0.
